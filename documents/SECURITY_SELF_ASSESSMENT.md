# Aegis 安全自评

> **范围声明。** Aegis 是面向比赛的原型系统，只使用虚构用户、账户和资金，不连接真实支付网络，也不是生产银行系统。本文区分已实现控制、模拟控制和生产环境缺口。本文是安全自评，不是渗透测试、认证或合规审计结论。

## 1. 总体结论

Aegis 把安全边界放在**金融核心（Banking Core）**，而不是语言模型。模型可以提出意图、参数和计划，但不能提供身份、风险等级、审批状态、MFA 验证码、授权凭据、余额或“已完成”事实。每一笔金融写入都由 Core 在数据库事务内重新校验并提交。

**总体判断：** 作为比赛原型，确定性控制面较强；在身份、传输安全、限流、集中审计、反欺诈监控和运维能力补齐之前，**不具备生产上线条件**。

| 领域 | 评估 | 摘要 |
|---|---|---|
| 权限分级 | 已实现 | Green / Yellow / Red 由 Core 策略执行；未知动作默认拒绝 |
| 审批绑定 | 已实现 | 负载哈希绑定、限时、一次性授权；提交时重新校验 |
| 幻觉防护 | 已实现，有边界 | 类型化工具、参数来源、计划校验、Core 唯一事实源；模型语义仍可能出错 |
| 提示注入 | 分层缓解 | 规则、模型信号、证据校验、能力收敛；不构成形式化保证 |
| 审计 | 部分实现 | 具备 Trace ID 与审计事件；缺少集中、防篡改、可保留的审计存储 |
| 安全锁定 | 部分实现 | 仅有 MFA 失败锁定；没有全局可疑行为或速度风控引擎 |
| 沙箱 | 不适用 | Agent 不执行模型生成代码，因此没有代码沙箱 |
| 金融完整性 | 已实现，有边界 | Decimal、幂等、行锁、复式账本；缺少余额与账本的定期对账 |
| 生产就绪 | 未达到 | 开发身份、静态令牌、HTTP 内部链路、无限流 |

## 2. 信任模型与执行边界

| 层级 | 信任级别 | 权限 |
|---|---|---|
| 用户、浏览器、上传文件、聊天文本 | 不可信 | 只能提出请求，不能授权 |
| 模型输出（LLM / Jev） | 不可信候选 | 可提出意图、槽位和计划，不能执行 |
| Agent 服务 | 受限编排者 | 拆解、校验，并仅调用已注册工具 |
| ToolGateway | 类型化边界 | 校验工具入参与出参，注入可信执行上下文 |
| 金融核心 | 权威来源 | 身份、归属、策略、审批、MFA、授权、账本 |
| PostgreSQL | 事实存储 | 约束、唯一键、行锁、账本只追加 |

浏览器不持有 Core 或 Agent 的服务令牌。Node 代理删除浏览器提交的 `Authorization`，注入服务端令牌。Agent 只通过类型化 HTTP 工具调用 Core，不直接写金融 ORM。

## 3. 权限分级实现

### 3.1 确定性策略权威

- `PolicyEngine.evaluate` 是风险等级的唯一来源；模型和前端不能自行指定。
- 前端只展示 Core 返回的等级，并对所有敏感操作复用同一个 Shield 审批组件。
- 未知动作和没有显式策略的动作一律 **DENIED**。
- 风险审批不等于资金已提交。完整链路是：**参数确认 → 风险审批 → 一次性授权 → Core 提交**。
- 审批绑定操作者、业务操作、动作、负载哈希和有效期；授权凭据只能消费一次。
- 提交时，Core 重新检查归属、业务状态、审批状态、授权负载哈希、有效期和当前风险等级。

### 3.2 分级矩阵

| 操作 | 等级 | 执行方式 | 状态 |
|---|---|---|---|
| 账户、余额、流水、消费、预算、订阅、银行卡、理财产品与持仓、收款人查询 | Green | Core 认证读取与归属检查 | 已实现 |
| 转账，当日累计转出 ≤ 1,000 元 | Yellow | 用户明确确认后签发一次性授权 | 已实现 |
| 转账，当日累计转出 > 1,000 元 | Red | 模拟六位码 MFA 后签发一次性授权 | 已实现 |
| 银行卡冻结、解冻、消费限额调整 | Yellow | 明确确认后签发一次性授权 | 已实现 |
| 银行卡挂失 | Red | 模拟 MFA 后签发一次性授权 | 已实现 |
| 订阅取消 | Yellow | 明确确认后签发一次性授权 | 已实现 |
| 储蓄罐单次存入 ≤ 1,000 元 | Yellow | 明确确认后签发一次性授权 | 已实现 |
| 储蓄罐单次存入 > 1,000 元 | Red | 模拟 MFA 后签发一次性授权 | 已实现 |
| 理财申购与赎回 | Red | 模拟 MFA 后签发一次性授权 | 已实现 |
| 虚拟卡申请 | 策略中为 Yellow | 没有端到端接口或页面流程 | 未实现 |
| 修改密码 | 策略中为 Red | 没有端到端接口或页面流程 | 未实现 |
| 其他动作 | — | 失败关闭 | 已实现（`DENIED`） |

**阈值语义。** 转账日限额按 `Asia/Shanghai` 业务日计算，包含仍可提交的 `PENDING_AUTHORIZATION`、`AUTHORIZED` 草稿，以及 `PROCESSING`、`COMPLETED` 转账；已过期、已取消和失败草稿不占用额度。累计金额**恰好 1,000 元为 Yellow**，超过 1,000 元为 Red。提交转账时会再次计算累计额，因此 Yellow 审批不能在当日累计额跨过 Red 阈值后继续使用。

### 3.3 审批与 MFA 控制

| 控制 | 实现 |
|---|---|
| 审批有效期 | 最长 10 分钟，且不晚于草稿过期时间 |
| 授权凭据 | 一次性、绑定负载哈希、绑定业务操作、绑定操作者 |
| MFA 挑战 | 六位码、5 分钟有效、3 次尝试，失败后锁定 15 分钟 |
| MFA 存储 | 加盐 PBKDF2-HMAC-SHA256 哈希；不保存明文验证码 |
| 重放防护 | 已消费授权和已确认审批不能复用 |
| 篡改防护 | 修改金额、账户、收款人或操作类型会使旧授权失效 |
| 模型隔离 | MFA 验证码和授权凭据不进入模型上下文 |

### 3.4 场景覆盖

| 比赛场景 | 覆盖情况 | 与安全相关的缺口 |
|---|---|---|
| 智能转账 | 部分实现 | 支持已保存收款人的姓名/昵称、AA 分摊计算和收款人排序；不支持手机号、备注转账、预约转账和多收款人收款。 |
| 账单分析 | 部分实现 | 支持分类分析、月度汇总和消费汇总；没有年度报告，异常消费逻辑未作为一级控制暴露。 |
| 理财操作 | 已实现 | 支持风险测评、推荐、比较、申购、赎回和适当性校验。 |
| 卡片管理 | 部分实现 | 支持限额、冻结/解冻和挂失；卡片申请仅有策略项，没有业务流程。 |
| 订阅代扣 | 已实现 | 支持周期扣款识别、续费提醒和经确认的取消。 |
| 跨场景编排 | 部分实现 | 支持最多 5 个有依赖的任务项和基于已验证余额的百分比转账；没有生日识别、商户下单和对话式储蓄执行。 |

## 4. 安全机制

### 4.1 幻觉与虚假结果防护

**控制。** 模型输出受 Pydantic 契约和字段白名单约束；任务拆解要求引用当前消息中的原文证据；`CapabilityBroker` 按意图收敛可用工具；`PlanVerifier` 拒绝未知工具、环路、过深 DAG、缺失来源、模型推断的金融参数和 Schema 违规；`ToolGateway` 同时校验入参与出参；`SafeResponseGenerator` 只用已验证工具结果组织文字，绝不会把待审批草稿描述为已完成；金融事实只来自 Core。

**残余风险。** 系统可能误解请求并追问错误问题，但不能把误解转化为越权或虚假的金融成功。模型的语义准确率是概率性的，Core 的权威性是确定性的。

### 4.2 提示注入

**控制。** 输入契约拒绝密码、OTP/MFA 验证码、CVV 和完整卡号；规则路由识别显式“忽略规则/绕过审批”等标记并失败关闭；任务拆解同时使用 Jev 注入概率和显式绕过标记；前端执行独立的注入检查；模型提出的可信字段被拒绝；Agent 只能调用当前意图允许的工具；即使注入成功，也不能自行签发 Core 授权。

**残余风险。** 正则和分类器信号无法覆盖所有改写、编码和多轮注入。因此安全主张是**后果收敛**，不是检测完备：被注入的模型仍可能浪费一轮对话或生成错误计划，但不能绕过 Core 审批。

### 4.3 决策与执行日志

**控制。** 每个请求携带 `X-Trace-Id`；Core 为审批、转账、储蓄存入、卡片操作、理财订单、订阅取消和拒绝请求写入审计事件；Agent 持久化任务和单调事件；LangGraph checkpoint 保存可恢复执行状态；ToolGateway 记录操作者、Trace、工具名、结果状态和错误码。

**缺口。** ToolGateway 默认写入进程日志，而不是持久审计存储；没有集中 SIEM、防篡改日志链、保留策略或审计复核台。Core 的失败审计把请求归因到配置的开发用户，不适合生产。这些是已知生产缺口，不能据此宣称决策链已完整留痕。

### 4.4 安全锁定与可疑行为

**已实现。** MFA 连续失败 3 次后锁定操作者 15 分钟；MFA 挑战限时且一次性；转账日限额阻止同一天无限升级转账。

**未实现。** 没有全局反欺诈引擎、速度检查、设备指纹、地域异常规则或基于可疑行为的自动账户冻结。`safety_locks.failure_count` 没有作为全局升级阈值使用。日限额是金融控制，不是反欺诈系统。

### 4.5 沙箱

Agent 不执行模型生成的代码。模型只输出结构化意图、槽位和经过校验的 `TaskPlan`；执行范围仅限已注册的类型化工具。系统中没有对模型输出执行 `eval`、动态导入或任意 Shell。按当前架构，代码执行沙箱要求通过**消除代码执行**来满足，而不是提供一个沙箱。

如果未来引入模型生成代码或任意脚本，必须增加具备资源限制、网络隔离、系统调用过滤和出站监控的专用沙箱。上传的票据图片和音频会校验大小、MIME 和文件签名，但没有恶意软件扫描。

### 4.6 金融完整性

| 控制 | 实现 |
|---|---|
| 金额运算 | Python `Decimal`，PostgreSQL `NUMERIC(18,2)`；不使用二进制浮点 |
| 幂等 | 转账、理财订单、储蓄罐、出资和消费记录均有唯一键 |
| 并发 | 对草稿、账户、审批和持仓加行锁，并按固定顺序处理 |
| 复式账本 | 每笔转账写入借贷平衡分录，提交前校验平衡 |
| 账本不可变 | PostgreSQL 触发器拒绝更新和删除已入账分录 |
| 归属 | Core 重新检查账户、银行卡、储蓄罐、订单和收款人归属 |
| 状态完整性 | 明确转账、审批和订单状态迁移；终态重放安全 |

**残余风险。** 账户余额是存储投影，与账本在同一事务内更新；没有定期的账本到余额对账任务，因此缺少独立漂移检测。授权凭据在最终余额检查前被消费，失败提交可能需要重新审批。`PROCESSING` 到 `COMPLETED` 之间发生崩溃时没有专用恢复任务。

### 4.7 身份、传输与密钥

**已实现。** `.env` 未纳入版本控制；密钥使用 `SecretStr`；浏览器不持有服务令牌；Node 代理限制来源并注入令牌；设置 CSP、`nosniff`、`no-referrer` 和 `Cache-Control: no-store`；授权凭据只存在于内存，并在前端 API 日志中脱敏。

**模拟或缺口。** 身份是绑定单个配置用户的开发桩和静态服务令牌；没有用户登录、OAuth/OIDC、RBAC、令牌轮换、mTLS 或 Agent 与 Core 之间的 TLS。非开发模式会以 `401` 失败关闭。没有应用层限流或 WAF。任何非本地部署前都必须补齐这些控制。

### 4.8 隐私与数据最小化

**控制。** 输入防线拒绝认证秘密；可选隐私代理在模型出站前替换邮箱、手机号、UUID、类卡号、类账号和配置姓名；消费标注工作线程只发送符合条件的商户描述，且要求不含数字、标识符或替换项；本地票据 OCR 为默认路径，后端视觉与语音为显式启用；Agent 只发送完成任务所需的最小上下文。

**残余风险。** 隐私代理只覆盖标识符，且是尽力而为。启用 LLM、Jev 或多媒体能力时，金额、商户、日期和自由文本姓名仍可能到达外部服务。供应商数据处理条款、区域存储和删除保证属于部署责任，不是本仓库的固有属性。

## 5. 已知风险清单

严重度按生产部署后的残余风险评定；比赛原型使用虚构数据。

| 编号 | 风险 | 影响 | 严重度 | 现有缓解 | 需要补齐 |
|---|---|---|---|---|---|
| R-01 | 开发身份且无 RBAC | 所有用户映射到单一配置操作者，跨用户隔离依赖该桩 | 严重 | 静态服务令牌、开发模式限制、Core 归属检查 | OIDC/SSO、用户会话、角色、租户隔离 |
| R-02 | 无 TLS/mTLS、静态服务令牌 | 共享网络中的凭据窃取或流量截获 | 高 | 本地 HTTP 边界、代理注入令牌、`.env` 未跟踪 | TLS/mTLS、密钥管理、轮换、网络策略 |
| R-03 | 无 API 限流或反自动化 | 暴力尝试、成本耗尽、拒绝服务 | 高 | 请求截止时间、供应商重试、MFA 尝试锁定 | 网关限流、配额、机器人检测、告警 |
| R-04 | 提示注入仍可能以变体成功 | 模型被操纵、浪费轮次、生成错误计划 | 高 | 分层过滤、证据校验、能力收敛、Core 权威 | 红队语料、分类器评估、回归门禁 |
| R-05 | 无全局反欺诈或速度引擎 | 日限额以下的重复可疑操作 | 高 | 日累计限额、MFA 锁定 | 反欺诈规则、设备/行为分析、复核队列 |
| R-06 | 审计未集中、非防篡改 | 调查证据不完整、保留不足 | 高 | Trace ID、Core 审计事件、Agent 事件、checkpoint | 只追加审计存储、SIEM、保留策略、访问控制 |
| R-07 | 余额为投影且无对账 | 未来缺陷或人工改动后无法发现漂移 | 高 | 同事务更新、账本平衡校验、数据库约束 | 定期对账、差异告警、修复手册 |
| R-08 | 授权在最终余额检查前被消费 | 失败提交会消耗审批 | 中 | 要求重新审批；资金未移动 | 所有前置条件通过后再消费授权 |
| R-09 | `PROCESSING` 到 `COMPLETED` 的崩溃窗口 | 转账可能卡在中间状态 | 中 | 事务回滚、状态查询 | 恢复任务、幂等修复、运维告警 |
| R-10 | 未知结果对账不完整 | 部分写操作需要人工对账 | 中 | 转账、理财、卡片状态查询 | 增加储蓄和取消路径的对账 |
| R-11 | 没有代码沙箱 | 未来模型生成代码将不安全 | 中 | 当前不执行模型代码 | 仅在未来引入代码执行时增加沙箱 |
| R-12 | 隐私代理仅覆盖标识符 | 金额、商户、日期和姓名可能外发 | 高 | 脱敏与发送资格策略 | 数据分级、供应商 DPA、区域控制 |
| R-13 | 外部 LLM/Jev/OCR 治理不足 | 第三方保留数据和跨境传输 | 高 | 功能默认关闭、最小负载 | 供应商评估、合同控制、审计日志 |
| R-14 | MFA 为模拟实现 | 不是真实第二因素 | 中 | PBKDF2、过期、尝试上限、锁定 | 生产环境接入短信/TOTP/Passkey |
| R-15 | 读操作未统一经过 `PolicyEngine` | 未来策略覆盖不一致 | 中 | 认证与归属检查 | 统一读策略中间件或显式审查 |
| R-16 | 无 SCA/SBOM 或漏洞门禁 | 供应链暴露 | 中 | 固定依赖、锁文件 | SCA、SBOM、签名构建、补丁 SLA |
| R-17 | 缺少备份、灾备和数据库权限隔离 | 数据丢失或过度授权 | 高 | 事务、约束、迁移控制 | 备份、恢复演练、最小权限数据库角色 |
| R-18 | 产品覆盖缺口 | 预约转账、卡片申请、年度报告、跨场景下单 | 中 | 明确延期并进入澄清 | 每条新流程配套安全评审 |

在目标修订版本执行：

```bash
python -m pytest
python -m ruff check .
python -m mypy

cd frontend/aegis-pwa
npm run typecheck
npm test
npm run build
```
